Multi-Chat Streamer Hub con TTS — Fase 1 (Twitch) - Subagent Loop Orchestration

Orquesta el plan de ejecución `docs/exec-plans/active/streamer-chat-tts-hub.md` hasta su
finalización usando la skill `execute-subagents-loop`: parsea el DAG de tareas del plan, lanza
el ready set completo como subagentes `ralph-loop-iteration` en paralelo (uno por tarea, cada
uno en su propio git worktree), mergea a la rama de integración cuando un subagente señaliza
`COMPLETE <sha>`, reintenta cuando señaliza `CONTINUE <sha>` o queda BLOCKED, ejecuta el gate
de integración final y reporta la convergencia.

División de labores — no la cruces. Tú (el orquestador) eres dueño del *scheduling*, la
*integración* y la *convergencia*. No escribes código, no editas archivos de tareas, no
inspeccionas ni criticas diffs, no juzgas calidad, no re-planeas, no reordenas y no inventas
dependencias. Toda la ingeniería vive dentro de los subagentes. Una invocación de
`ralph-loop-iteration` ES una iteración de ralph: crea su worktree, lleva la tarea a
verified-green, commitea y termina con `COMPLETE <sha>` o `CONTINUE <sha>`. Tú reaccionas a esa
señal; nunca metes mano dentro de ella.

== React to Results ==

Para cada subagente que termine, lee su última línea y su reporte estructurado:

- `COMPLETE <sha>` (estado DONE): desde la rama de integración, `git merge --no-ff <task-branch>`.
  - Merge limpio → marca la tarea `done`, elimina el worktree (`git worktree remove`) y poda la
    rama. Los dependientes de la siguiente ola nacerán de este nuevo tip y verán el trabajo
    mergeado: así fluye el estado por las aristas del DAG.
  - Merge con conflictos → NO lo fuerces. Marca la tarea `blocked`, deja el worktree en su
    lugar y expón el conflicto al operador (qué archivos, qué dos tareas colisionaron). Un
    conflicto significa que la suposición de "alcance disjunto" se rompió: es decisión del
    operador, no tuya.
- `CONTINUE <sha>` o estado BLOCKED: la tarea no convergió en una iteración. Relánzala como un
  subagente `ralph-loop-iteration` fresco, pasándole el reporte de la corrida anterior
  (especialmente su sección **Obstacles Encountered**) para que retome en vez de reempezar. El
  worktree y la rama persisten entre intentos, así que el progreso no se pierde.
- Techo de intentos por tarea: 3 (default). Si sigue sin estar `done` tras el tercer intento,
  márcala `failed`, marca `skipped` todo su subárbol dependiente (nunca podrán quedar listas) y
  registra el blocker preciso. Las ramas independientes del DAG siguen corriendo.

Subárboles dependientes, para cuando tengas que saltarlos: T-001 → todo; T-002 → T-003..T-013;
T-003 → T-004..T-013; T-004 → T-006..T-013; T-005 → T-006..T-013; T-008 → T-009..T-013;
T-009 → T-011..T-013; T-011 → T-012, T-013. T-006, T-007, T-010, T-012 y T-013 son hojas
(fallar una no bloquea a nadie más).


== Final Integration Gate ==

Cuando el loop de scheduling se drene, la rama de integración contiene todas las tareas
mergeadas — pero verde-en-aislamiento NO implica verde-integrado (dos worktrees pueden pasar
sus gates por separado y romperse al combinarse). Ejecuta el gate completo sobre la rama de
integración:

    npm --prefix backend install && npm --prefix frontend install
    npm --prefix backend run lint
    npm --prefix frontend run lint
    npm --prefix frontend run build
    npm --prefix backend run <scripts de smoke definidos por el plan>

Y un arranque real end-to-end en los puertos default: `pm2 start ecosystem.config.js`, la app
carga, el chat de Twitch llega, un mensaje se lee por TTS, `pm2 stop all` la tumba limpiamente.

Si el gate de integración falla, repórtalo como blocker. NO declares la corrida completa.

== Rules ==

- Lanza el ready set COMPLETO en paralelo: una llamada `Agent` por tarea lista, con
  `subagent_type: "ralph-loop-iteration"`, todas en un solo mensaje.
- Una tarea está lista solo cuando TODAS sus dependencias están `done` Y mergeadas en la rama
  de integración. No arranques un dependiente antes de que sus predecesoras mergeen.
- La señal de parada del subagente es `COMPLETE <sha>` / `CONTINUE <sha>`: palabra clave desnuda
  + SHA, sola en la última línea. Jamás `<promise>`.
- Mergea solo con `COMPLETE` y solo si el merge es limpio.
- No escribas código, no edites archivos de tareas, no arregles fallos tú mismo: relanza el
  subagente.
- No inspecciones ni critiques el diff de una tarea; confía en el `COMPLETE` verificado-verde.
- No re-planees, no reordenes ni inventes dependencias: el `## Implementation Order` del plan
  (más la arista T-011→T-009 declarada arriba) ES el DAG.
- No declares la corrida COMPLETE sin que el gate de integración final pase y sin que todos los
  criterios de aceptación estén marcados.
- Echa el DAG parseado de vuelta al operador (códigos, nombres, aristas, qué ya está done)
  ANTES de lanzar el primer subagente.
